# 配电终端统一运维工具协议层 SDK 接口设计 V1.4 到 V1.5 改动点
## 1. 总体变化

V1.5 在 V1.4 基础上补入文件写取消设计，明确把取消能力收敛为写文件方向的独立入口，而不是塞回读写共用的文件抽象里。此次调整后：

- 新增 `<prefix>_cancel_file_write`，仅用于中止正在进行的写文件传输。
- 读文件不新增取消入口，读文件流程继续保持“读取 - 分块回调 - 最终结果”这一路径。
- 运维101、标准101、标准104 继续按同一套 `<prefix>` 命名风格暴露接口，分别对应 `m101_`、`iec101_`、`iec104_`。
- 文件传输状态与结果补充取消态和取消结果码，用于区分“主动取消”与“普通失败/超时/拒绝”。

本次变化的核心是把“取消”从隐式异常收敛改成显式控制动作；调用方在写文件方向可以单独终止传输，但读取方向仍按完整读流程处理。

## 2. 调整依据

V1.4 仅保留文件目录、文件读取、文件写入、写文件断点续传和状态查询能力，取消语义没有作为独立入口暴露。对于写文件场景，这会让“终止进行中的写传输”只能依赖超时、链路异常或对端否定确认收敛，调用方无法表达主动取消意图。

V1.5 只在写文件方向补一个独立取消入口，原因有两点：

- 写文件是顺序推进的有状态过程，取消属于控制面动作，不应混入文件读取语义。
- 读文件天然是远端到本地的获取过程，当前设计不要求给它单独增加取消入口。

## 3. 文件写入接口变化

| 变化项 | V1.4 | V1.5 | 影响 |
| --- | --- | --- | --- |
| 写文件取消入口 | 无独立取消 API | 新增 `<prefix>_cancel_file_write` | 调用方可以显式中止进行中的写传输 |
| 入口归属 | 文件写入与取消语义混在同一抽象里理解 | 取消是写文件方向的独立控制动作 | 写文件主流程不需要吸收读文件取消语义 |
| 命名风格 | 各协议族按各自前缀暴露常规文件 API | 101/104 继续沿用同一前缀风格：`m101_`、`iec101_`、`iec104_` | 不引入新的协议专属命名分支 |
| 读文件取消入口 | 无 | 仍无 | 读文件保持原有完整读取模型 |

V1.5 的文件写取消只补“入口”，不改写文件主请求的职责边界。写文件仍负责发起和推进内容传输，取消入口只负责终止正在进行的写传输。

```c
typedef struct iec_file_write_cancel_request {
    uint16_t common_address;       /* 目标公共地址 */
    uint32_t transfer_id;          /* 待取消的写文件传输 ID，来自 write_file 返回值 */
    uint32_t command_timeout_ms;   /* 取消命令确认超时 */
} iec_file_write_cancel_request_t;

/* 写文件取消是独立入口。
 * m101、iec101、iec104 三套库均按同形前缀导出：
 * m101_cancel_file_write / iec101_cancel_file_write / iec104_cancel_file_write。
 * 它只中止写文件方向的进行中传输，不改动读文件流程，也不把取消塞回写文件主请求。
 */
iec_status_t <prefix>_cancel_file_write(
    iec_session_t *session,
    const iec_file_write_cancel_request_t *request,
    uint32_t *out_request_id);
```

## 4. 状态和结果语义变化

| 变化项 | V1.4 | V1.5 | 影响 |
| --- | --- | --- | --- |
| 文件传输状态 | 仅有已受理、传输中、已完成、失败 | 新增取消态 | 状态快照可以明确表示写传输已被取消 |
| 文件结果码 | 仅有成功、拒绝、否定确认、偏移不匹配、超时、协议错误、未找到、不支持等结果 | 新增取消结果码 | 最终结果可以区分“取消”与“普通失败” |
| 最终结果通道 | `on_file_operation_result` | 仍然使用 `on_file_operation_result` | 不新增独立取消回调 |

语义上，取消态是写文件方向的终态，不是读文件终态，也不是新的中间态。调用方不要把“取消请求已发出”理解成“取消已经完成”；最终是否真正取消，仍要以文件结果回调为准。

```c
typedef enum iec_file_transfer_state {
    ...
    IEC_FILE_TRANSFER_STATE_CANCELED = 5   /* 传输已取消 */
} iec_file_transfer_state_t;

typedef enum iec_file_result_code {
    ...
    IEC_FILE_RESULT_CANCELED = 10          /* 写文件取消已被接受 */
} iec_file_result_code_t;

/* 取消态只用于写文件方向的终结状态。
 * 结果回调仍然是最终判定依据，不能用请求已发送来代替取消完成。
 */
```

## 5. 文件读取边界

| 变化项 | V1.4 | V1.5 | 影响 |
| --- | --- | --- | --- |
| `<prefix>_read_file` | 普通远端文件读取 | 普通远端文件读取 | 不新增取消入口 |
| `on_file_data_indication` | 按块返回读取数据 | 按块返回读取数据 | 回调语义不变 |
| 读文件状态收敛 | 读取最终结果由文件结果回调收敛 | 仍然如此 | 读文件继续按完整读取流程结束 |

V1.5 不给读文件补取消分支。读文件仍然通过 `on_file_data_indication` 聚合数据块，再由 `on_file_operation_result` 判断最终结果；取消逻辑仅出现在写文件方向。

## 6. 流程章节变化

| 章节 | V1.4 | V1.5 | 影响 |
| --- | --- | --- | --- |
| 文件读取流程 | 读取、分块回调、最终结果 | 不变 | 读文件不增加取消分支 |
| 文件写入流程 | 写入、续传、最终结果 | 补入独立取消步骤 | 写文件可由调用方显式终止 |
| 状态查询流程 | 本地状态快照 | 继续保留，新增取消态可见性 | 状态展示可反映写取消终态 |

V1.5 的推荐写文件流程如下：

1. 调用 `<prefix>_write_file` 发起写文件传输。
2. 如果业务上需要终止写入，调用同一协议族前缀下的 `<prefix>_cancel_file_write`。
3. 通过 `on_file_operation_result` 获取取消是否被接受、是否真正进入取消终态以及最终结果码。
4. 读取文件流程不变，不走取消入口。

## 7. 调用方影响

- 调用方如果要主动停掉正在进行的写传输，应改用 `<prefix>_cancel_file_write`，不要再把取消意图混进 `<prefix>_write_file` 的正常写入参数里。
- 101 和 104 的调用方式保持一致，只是导出前缀分别是 `m101_`、`iec101_`、`iec104_`。
- 读文件调用方不需要补充取消分支，仍按文件数据块和最终结果回调收敛。
- 如果取消被拒绝、超时或对端不支持，调用方仍要依赖既有失败结果码和文件结果回调做排障，不要把它误判成已取消。

## 8. 发布基线影响

本次变化涉及新增对外 API、文件状态枚举和文件结果码，后续落地时需要同步 public headers、实现、测试和 `cmake/api_exports.txt`。发布基线未纳入之前，不应在别处补写假实现或占位实现。
